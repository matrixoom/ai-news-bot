# Task 05: Testing, Release And Operations

## 目标

把项目从“能跑脚本”推进到“可持续演进的自动化任务”。

## 本阶段交付

- 单元测试
- 集成测试
- 测试夹具与 mock
- GitHub Actions 校验
- 配置迁移文档

## 任务拆解

### 1. 引入测试框架

建议使用 `pytest`，至少覆盖以下模块：

- 配置解析
- RSS / 搜索结果标准化
- 去重逻辑
- 当日过滤逻辑
- 市场指标计算
- 鱼盆模型判定
- 报告装配

### 2. 设计 mock 策略

必须对这些外部依赖做 mock：

- RSS 请求
- 搜索请求
- LLM API
- 豆包 API
- 市场数据 API
- 各类通知器

### 3. 增加集成测试

建议准备一套固定样本数据，验证：

- 输入样本新闻后能生成稳定报告
- 开启 / 关闭某些模块时，输出结构符合预期
- 无法获取某个外部数据源时，系统能降级

### 4. GitHub Actions 调整

建议拆分工作流：

- `test.yml`
- `daily-news.yml`

测试工作流负责：

- 安装依赖
- 运行单元测试
- 校验基础导入和配置合法性

### 5. 配置治理

当前配置主要靠 `.env` 和 `config.yaml` 拼接，后面模块多了以后容易失控。

建议补齐：

- `.env.example`
- `config.yaml` 注释
- README 配置说明
- secrets 对照表

### 6. 监控与失败处理

建议新增：

- 模块级执行耗时日志
- 数据源失败统计
- 报告生成失败原因分类
- GitHub Actions 失败告警策略

## 验收标准

- 核心模块测试可自动运行
- PR 或主分支变更时可先跑测试
- GitHub Actions 能稳定完成最小任务链路
- README 和配置示例与代码一致

## 风险

- 如果前面几个阶段不先把结构拆开，测试成本会很高
- 外部 API 过多时，集成测试必须严格控制在 mock 模式

## 建议优先级

P0，从第一阶段开始同步建设，不要最后补。
