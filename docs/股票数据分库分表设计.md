
## market_stock_daily_bar 分库规则

背景

当前 market_data.db 中的 market_stock_daily_bar 表用于存储 A 股股票、ETF 的日线行情数据。随着全市场股票和 ETF 的历史日线数据持续累积，该表数据量会快速增大。

问题包括：

1. 单个 SQLite 数据库文件越来越大，不利于本地开发、备份和迁移。
2. 单表数据量过大，查询、导入、VACUUM、索引维护成本上升。
3. GitHub 对单文件大小有限制，大型 SQLite 文件不适合直接上传和版本管理。
4. 后续持续增量拉取行情数据时，单库写入和管理压力集中。

因此需要对 market_stock_daily_bar 表进行分库处理。

本方案采用：

交易所缩写 + 股票代码特定位

作为分库规则。

`market_data.db` 中的 `market_stock_daily_bar` 数据量会很大，需要按 `symbol` 拆分到多个 SQLite 分库中。

`symbol` 格式：

```text
股票代码.交易所缩写
```

示例：

```text
600519.SH
000010.SZ
920118.BJ
```

---

## 1. 非 BJ 交易所分库规则

适用于：

```text
SH
SZ
```

分库规则：

```text
market_stock_{交易所缩写}_{股票代码第4和第5位}.db
```

股票代码位置从 1 开始：

```text
code = 600519
位置 = 123456
第4和第5位 = 51
```

示例：

| symbol      | code     | exchange | 第4和第5位 | 分库文件                    |
| ----------- | -------- | -------- | ------ | ----------------------- |
| `600519.SH` | `600519` | `SH`     | `51`   | `market_stock_SH_51.db` |
| `588000.SH` | `588000` | `SH`     | `00`   | `market_stock_SH_00.db` |
| `000010.SZ` | `000010` | `SZ`     | `01`   | `market_stock_SZ_01.db` |
| `300750.SZ` | `300750` | `SZ`     | `75`   | `market_stock_SZ_75.db` |
| `159915.SZ` | `159915` | `SZ`     | `91`   | `market_stock_SZ_91.db` |

---

## 2. BJ 交易所分库规则

适用于：

```text
BJ
```

分库规则：

```text
market_stock_{交易所缩写}_{股票代码最后1位}.db
```

示例：

| symbol      | code     | exchange | 最后一位 | 分库文件                   |
| ----------- | -------- | -------- | ---- | ---------------------- |
| `920118.BJ` | `920118` | `BJ`     | `8`  | `market_stock_BJ_8.db` |
| `920099.BJ` | `920099` | `BJ`     | `9`  | `market_stock_BJ_9.db` |
| `920010.BJ` | `920010` | `BJ`     | `0`  | `market_stock_BJ_0.db` |

## 3. 统一路由逻辑

```python
def resolve_market_stock_shard_db(symbol: str) -> str:
    if not symbol or symbol.count(".") != 1:
        raise ValueError(f"Invalid symbol format: {symbol}")

    code, exchange = symbol.split(".", 1)

    if len(code) != 6 or not code.isdigit():
        raise ValueError(f"Invalid stock code: {code}")
    if exchange not in {"SH", "SZ", "BJ"}:
        raise ValueError(f"Unsupported exchange: {exchange}")

    if exchange == "BJ":
        shard_key = code[-1]
    else:
        shard_key = code[3:5]

    return f"market_stock_{exchange}_{shard_key}.db"
```

## 5. 分库数量上限

```text
SH：最多 100 个，market_stock_SH_00.db ~ market_stock_SH_99.db
SZ：最多 100 个，market_stock_SZ_00.db ~ market_stock_SZ_99.db
BJ：最多 10 个，market_stock_BJ_0.db ~ market_stock_BJ_9.db
```

总理论上限：

```text
210 个分库
```

所有分库中表名保持一致：

```text
market_stock_daily_bar
```

即：

```text
market_stock_SH_51.db
  └── market_stock_daily_bar

market_stock_SZ_75.db
  └── market_stock_daily_bar

market_stock_BJ_8.db
  └── market_stock_daily_bar
```

## 6. 主库与分片库职责

所有数据库文件统一位于主库同目录，默认是 `.data/`。

`market_data.db` 继续保存：

- `market_stock_instrument`
- `market_stock_profile`
- `market_stock_financial_metric`
- `market_stock_sync_state`

210 个 `market_stock_*.db` 只保存：

- `market_stock_daily_bar`
- `idx_market_stock_daily_bar_symbol_date`

SQLite 不支持跨数据库文件外键，因此分片表不声明指向
`market_data.db.market_stock_instrument` 的外键。仓储层通过严格 symbol 校验和标的同步流程维持一致性，
分片表继续使用 `(symbol, trade_date)` 主键保证幂等。

---

## 7. 读写与列表查询

- 日线写入、存在性判断和日期范围读取均先调用统一路由函数，再访问单个目标分片。
- 同步状态仍写入 `market_data.db`，日线写入成功后从目标分片聚合最早日期、最新日期和点位数。
- 股票列表先在主库分页查询标的，再按当前页 symbol 所属分片分组；每个分片执行一次批量最新价查询，避免逐标的 N+1。
- 运行时访问某个缺失分片时会自动创建统一表和索引，保证单库缺失可自愈。

---

## 8. 旧表迁移策略

`StockMarketRepository` 初始化时会检测主库是否仍存在旧
`market_stock_daily_bar`：

1. 先校验全部 distinct symbol，未知交易所或非法代码立即失败。
2. 按分片分组，每批 1000 行幂等写入目标库。
3. 每个分片校验目标记录数不少于源记录数。
4. 校验全部源记录均已处理后，才从主库删除旧表并执行 `VACUUM`。
5. 任一步失败时保留主库旧表；已复制的分片记录可在下次初始化时通过 upsert 安全重试。

迁移不改变前端 API 或 Service 调用接口。
